# Canonical Media/Video Publication — Constitution-Compliant Design

## Decision

Implement the approved Media/Video publication workflow without changing the
NHK V3 constitutional ownership boundaries or replacing the existing Unified
Admin Workbench. Video remains a canonical external reference with a persisted
Public Identity route at `/video/{slug}/`. YouTube remains source/provenance
and embed data; it is never the primary frontend destination.

Media continues to be split into Media, MediaAsset and MediaUsage. The public
projection may expose eligible image assets through the existing gallery,
entity and usage surfaces. A standalone indexable Media detail route is not
implemented in this slice because the current Constitution and Media/Image SEO
contract do not authorize one; the requested `/hinh-anh/{slug}-.../` shape is a
`CONSTITUTION_CONFLICT` until an approved amendment changes that boundary.

## Boundaries and data flow

Canonical owners remain unchanged:

`Authority / Knowledge / Source-Evidence / Graph / Media / Video`
`→ existing application services and governed writers`
`→ read-only Admin adapters and public projection queries`
`→ WordPress templates and SEO serializers`.

Admin reads are composed from existing repositories/services. Semantic writes
continue through Governance and Controlled Apply. The Admin layer must not
create a proposal, evidence chain, Graph edge, Media identity or Video record
directly. Existing `VideoRelationAdminService`, `MediaService`,
`MediaVideoPageQuery`, `RelatedContentQuery`, Public Identity and SEO services
are reused.

## Admin experience

The Media workspace gets shared tabs for `Tất cả`, `Hình ảnh` and `Video`.
Video becomes a real sub-workspace with search by title, external ID and
canonical UUID, filters for publication/readiness/relation/evidence/frontend
state, a read-only list projection, and a detail shell with the eight requested
tabs. Image uses the same shared shell and adapters with image-specific fields
and current semantic-role vocabulary. Technical identifiers and raw payloads
remain inside the technical disclosure; normal workflows accept selected
canonical records and human-facing fields only.

“Xem trên web” is emitted only when the canonical public projection is eligible
and resolves to the first-party Video URL. “Mở nguồn gốc” is a separate action
for the external source. Missing projection is shown as an honest blocker and
never falls back to YouTube.

## Publication/read-back model

The UI maps existing canonical lifecycle/readiness/governance values to the
requested human labels without introducing a new semantic status enum. A record
is frontend-available only when canonical eligibility, public source/media,
editorial presentation, governed semantic attachment, Public Identity and
projection read-back all pass. Apply success alone remains distinct from
frontend availability. Private, unapproved, unavailable, duplicate and retired
records remain excluded or noindex according to existing policy.

## Video public projection

The Video detail projection renders breadcrumb, NHK title, player, supported
editorial description, related public Graph/projection sections, provenance and
first-party internal links. `VideoObject` and breadcrumb data are generated by
the existing SEO projection and include only real values; duration, upload date
and thumbnails are omitted when unavailable. Historic slugs use the existing
one-hop resolver.

## Testing and verification

Add failing tests before each new behavior for Admin tabs/search/detail/action
separation, Video route/read-back, projection visibility, SEO structured data,
lifecycle mapping and the `truOChTNbwA` regression fixture. Run focused tests,
full Unit, guarded Integration when available, PHP/JS syntax checks, Composer
validation and `git diff --check`. No seed, migration, Graph JSON mutation,
legacy repair, production publish or external deployment is included.
